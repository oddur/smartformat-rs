# How compatibility is verified

The expected output of every compatibility test is generated by SmartFormat.NET itself, not
written by hand. A C# console app in `tools/goldens` renders a table of templates with the
real 3.6.1 library and prints the results as JSON; the Rust suite replays the same table and
requires byte equality. Of 2,833 cases, 2,764 match and 69 are skipped with a stated reason.

## Why the expectations are generated

A hand-written expectation records what the person writing the test believed .NET does. For
the cases that matter, nobody knows.

`{0:F}` on 2.675 is `2.67`, because the nearest double to 2.675 is slightly below it and
.NET rounds the exact decimal expansion. French groups digits with U+202F and Russian with
U+00A0. Swedish and Finnish negate with U+2212 rather than a hyphen. Polish, Czech, Russian,
Ukrainian and Finnish inflect the month name next to a day number; German, Danish and
Norwegian do it only in the abbreviated form. A `FormattingException` message quotes the
template and points a caret at a specific index, in a specific layout. Each of those is a
coin flip for a human and a fact for the library.

Generating the answers also makes an upgrade legible. Bumping the pinned SmartFormat.NET
version and regenerating produces a diff that shows exactly which behaviors changed, rather
than a set of test failures somebody has to interpret.

The corpus is what makes the result meaningful, so it is built to be dense rather than
representative. The numeric, date, plural and culture groups are generated combinatorially,
crossing a value list or a culture list with a specifier list, which is where most of the
2,833 cases come from. The culture groups cross every shipped culture with the specifiers
whose output is *pure culture data*: `N`, `C` in both signs, `P1` and the `d`, `D`, `t`, `T`,
`f` date patterns. That is precisely the material no reviewer can check by eye.

## What the harness pins

Two processes have to agree on more than the template, so both sides are pinned to the same
inputs, and each pin is mirrored in the Rust runner:

- **The library version.** SmartFormat.NET 3.6.1 and SmartFormat.Extensions.Time 3.6.1, from
  `tools/goldens/goldens.csproj`. Where upstream has since changed behavior, the port
  follows 3.6.1.
- **Settings.** A case carries a `settings` object holding only the properties that differ
  from .NET's defaults, and the Rust runner reads the same keys. It covers `SmartSettings`
  ([error actions](../reference/settings-and-features.md#erroraction), case sensitivity,
  `string.Format` compatibility, alignment fill character,
  parser knobs) and the per-extension knobs that are not settings at all: the regex options,
  the split characters, the substring out-of-range behavior.
- **The culture.** Each case names the culture .NET rendered it with; `""` is the invariant
  one. A name the generated table does not carry fails the case. It is never a skip, because
  a missing culture must not look like a pass.
- **The clock.** Two things read a wall clock: `TimeFormatter` on a `DateTime`, and the date
  branch of `ConditionalFormatter`. The harness pins `SystemTime.Now()` before it renders
  anything, records the instant in the document, and the Rust runner puts that instant in
  `SmartSettings::now` for *every* case. A case that reads a clock is then as deterministic
  as one that does not.
- **Provider fixtures.** The localization table, the variables groups and the template set
  are written in source on both sides and mirrored entry for entry. The localization fixture
  is deliberately not the resx-backed .NET provider: a fixture that lives in a resource file
  cannot be mirrored in Rust, and a fixture whose contents differ between the two sides proves
  nothing.
- **Value types.** The JSON argument encoding names the CLR type it maps to, down to the
  cases where the type is the point. `$i32` asks for a 32-bit `int` rather than a `long`,
  because `X` and `B` render the CLR type's own width, and `$f` carries the non-finite doubles
  JSON has no form for.
- **The build.** The project treats warnings as errors, because a build warning on stdout
  would corrupt the JSON, and sets `InvariantGlobalization` to `false` explicitly, because an
  environment that turned it on would render every culture case as the invariant culture and
  look like agreement.

Two ordering hazards are enforced mechanically rather than by review. .NET's
`ListFormatter.CollectionIndex` is a static, so a case whose list iteration fails part-way
leaves it set for the rest of the process; the harness renders an `{Index}` canary after
every case and fails the build unless the only case that leaves it set is the last one in the
table. And the skip list is checked against the case table, so an entry naming a case that no
longer exists fails the suite instead of silently hiding nothing.

## What a skipped golden means

A skip is a record, not an omission. The case stays in the table and holds .NET's answer;
the Rust runner names its id in an explicit `SKIPPED` list with the reason; and every entry
under "Known divergences" in [DESIGN.md](../../DESIGN.md) points at one of those ids or at a
unit test. A skip reason states what .NET does, what the port does instead, and why the
difference is deliberate.

The reasons fall into a few groups. Some cases pin behavior outside the port's scope, such
as a custom numeric pattern rendering as literal text. Some pin a representational
difference, such as a 32-bit `int` rendering 32 bits of two's complement where every signed
integer here is an `i64`. Some pin a .NET answer the port refuses to produce, such as the CLR
type name of a list. Keeping the .NET answer checked in matters more than the pass mark: it
is the record of what closing the gap would have to reproduce, and it is re-derived from the
live library every time the goldens are regenerated.

Skips are per case id, which keeps a divergence from widening quietly. Broadening one turns a
passing case red, and the only way to make it green again is to add that id and its reason,
in the same change, next to the ledger entry.

## Why culture data comes from .NET, not CLDR

`tools/culturegen` reads `CultureInfo.NumberFormat` and `CultureInfo.DateTimeFormat` out of a
running .NET and prints them as Rust source. The port's culture table is therefore not
*mapped* from a standard; it *is* .NET's data, so for a listed culture the output matches by
construction rather than by testing.

Taking it from CLDR instead would have meant reconciling two things that do not need
reconciling. .NET's data is ICU-backed and mostly agrees with CLDR, and mostly is the
problem: the residue would be a permanent supply of one-character differences in exactly the
fields nobody inspects. The same reasoning settles pluralization, which is a port of
SmartFormat's own rule table rather than CLDR's. SmartFormat does not consult CLDR at runtime
either, and its table disagrees with CLDR in places (Icelandic is `one`/`other` there).

The cost is real and worth stating. The table holds 35 entries, the invariant culture
included, and a culture outside it is an error rather than a parent-culture guess. The data
is a snapshot of one ICU on one machine, so `generated.rs` and `goldens/m1.json` have to be
regenerated together, with the same SDK, on the same machine, in one commit; regenerating one
alone produces failures that look like port bugs. And one culture is knowingly wrong for
dates: `ar-SA` defaults to the Umm al-Qura calendar in .NET, and the port has only a
Gregorian one, so it feeds Gregorian fields through Hijri month names. Its numbers match.

## The limits of the method

The method proves one thing: for the cases in the table, under the settings in the table, the
two libraries produce the same bytes. It says nothing about a case nobody wrote. Byte equality
over a corpus is a statement about that corpus, which is why the corpus is dense and
combinatorial rather than illustrative.

Several classes of behavior cannot be goldens at all:

- **Anything reading ambient state.** Three .NET extensions stringify a value with the
  *thread* culture, so .NET's own answer depends on the machine it runs on. The `U` date
  specifier converts through the machine's timezone. There is no stable answer to compare
  against, so the harness stays clear of these and unit tests pin the port's side alone.
- **Anything unreachable through `Smart.Format`.** .NET's `TimeFormatter` mutates the parsed
  format it renders, so rendering one cached `Format` twice gives a different answer each
  time. No golden can reach that, because `Smart.Format(string, …)` reparses every call. A
  unit test records the difference instead.
- **Anything about a value .NET cannot represent.** A `TimeSpan` outside .NET's tick range has
  no .NET behavior to match, so the port's saturation is pinned only from its own side.

The .NET side is also one version and one ICU build. A different SmartFormat.NET, or the same
one on a machine with different culture data, is a different answer, which is exactly why both
artifacts are pinned and regenerated as a pair.

Two other suites sit alongside the goldens and cover what byte comparison cannot. The ported
NUnit tests carry SmartFormat.NET's own expectations for behavior that is easier to state
than to tabulate, and they run in CI with everything else. The fuzz targets under `fuzz/`
assert that the parser and the renderer never panic on arbitrary input; they are run by hand
rather than in CI, and they say nothing about output and nothing about memory, since an
unbounded alignment pad is a documented non-goal that both sides share.
